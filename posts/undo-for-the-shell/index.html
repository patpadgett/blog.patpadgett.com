undo for the shell, because rm has never once asked me if I was sure

I gave myself a dumb challenge: make the shell undo the last mv, cp or rm with no daemon, no root and no snapshots. It works. Read the damned limitations first.

I gave myself a dumb challenge on a slow night: make a shell that can undo the last thing you did, with no snapshotting filesystem[1]Ref. 1snapshotting filesystem en.wikipedia.org, no daemon, no root, and nothing installed but python3. You type mv, you type undo, the file goes back. That was the whole spec.

It came out to 410 lines of Python and 54 lines of bash, and you source it into your shell. It's on GitHub[2]Ref. 2undo on GitHub github.com. There is no PyPI package, because the thing is a shell function and pip can't reach into your .bashrc for you.

Before mv, cp, rm, chmod, chown, mkdir, rmdir or ln runs, a wrapper computes the inverse, writes it to a journal under ~/.undo, and then runs the real command. rm[3]Ref. 3rm(1) man7.org is the special one: nothing gets destroyed. The file moves into a trash directory[4]Ref. 4trash directory en.wikipedia.org and the journal remembers where it lived. Seven days later it's purged for real. undo -n shows you what would happen, undo -y does it, and undo -l lists the last ten so you can pick one.

The price: every mv now costs me 85 milliseconds instead of one, because two Python interpreters start up so I can feel safe. I measured it. I'm fine with it.

Things it will NOT save you from, and I wrote every one of them down in the README because I'd rather annoy you now than surprise you later: editor saves, redirects, anything under sudo, anything run from a script, and \rm, which bypasses an alias[5]Ref. 5alias en.wikipedia.org and does nothing at all to a shell function. If you want the real rm, type command rm. The README says best-effort recovery, in bold, and it is not a backup. Keep making backups, nimrod.

I have been typing rm for thirty years and it has never once asked me if I was fucking sure. Now I don't have to be.
